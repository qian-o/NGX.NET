# NGX.NET 代码风格重构设计文档

状态：草案。风格决策 S1 至 S7、结构决策 D1 至 D5 均已确定（§8）。结构决策以 Silk.NET、Vortice.Windows 的源码与 NGX SDK 头文件为依据，来源见 §8.4。

本文以**代码风格**为主线：手写代码、生成代码、生成器与验证代码，都要达到 `csharp-coding-standards.md`（下称“规范”，引用写作 规范 §n）的要求，并对齐 [Metal.NET](https://github.com/qian-o/Metal.NET) 与 [Zenith.NET](https://github.com/qian-o/Zenith.NET) 的写法。功能缺陷不是本文的出发点；涉及结构调整的内容集中在第 6 节。

## 0. 定位与约束

NGX.NET 是 NVIDIA NGX 的独立 C# 封装库，职责是：

1. 维护并分发二进制（NVIDIA 特性库与 `ngx-bridge`）。
2. 提供安全的 C# 方法：公共表面无指针，所有权清晰。

约束：

- 不依赖其他 NuGet 包（当前 `NGX.NET.csproj` 无 `PackageReference`；Roslynator 仅作为 `PrivateAssets=all` 的分析器）。因此 Vulkan 等 SDK 用到的类型必须自包含。
- 示例应用不在本文范围内。
- 保持现有公共 API 的语义，风格改造不改变调用行为；需要改变公共 API 的项单列在第 6、8 节。

## 2. 生成代码风格设计

### 2.1 总则

1. 生成文件只保留 `.g.cs` 后缀，不再输出头注释与 `#nullable enable`。
2. 不输出任何 `///`；需要补充信息时靠命名表达。
3. 所有 `using` 来自一个手写的 `Usings.cs`。
4. 输出本身满足规范的全部格式规则：Allman、成员之间空一行、`return` 前空一行、方法体块体、显式类型、`is null`/`is not` 等；`.editorconfig` 中针对生成目录的 `generated_code = false` 覆盖随头注释一起移除。
5. 目录按种类拆分：`Enums/`、`Structs/`（含 `Structs/Native/`）、`Delegates/`、`API/`；命名空间不体现这些目录（规范 §4）。

### 2.2 枚举

现状：

```csharp
// <auto-generated/>
// Generated by NGX.NET.Generator. Changes belong in the generator.

#nullable enable

namespace NGX.NET;

/// <summary>
/// NVSDK_NGX_Result
/// </summary>
public enum NGXResult : uint
{
    /// <summary>
    /// NVSDK_NGX_Result_Success
    /// </summary>
    Success = 1u,

    /// <summary>
    /// NVSDK_NGX_Result_Fail
    /// </summary>
    Fail = 3134193664u,
```

目标：

```csharp
namespace NGX.NET;

public enum NGXResult : uint
{
    Success = 1u,

    Fail = 0xBAD00000u,

    FailFeatureNotSupported = 0xBAD00001u
}
```

- 值对应原生值，因此保留显式值（规范 §5.6）。
- 超过一个字节且表示错误码的值输出为大写十六进制，与 `NGXException` 的 `0x{result:X8}` 消息一致（决策 S4）。

### 2.3 结构体

托管结构体：只有字段与（需要时）静态工厂；字段之间空一行；没有文档注释；字段名去掉 `p`/`pp`/`in`/`out` 前缀（S2）：

```csharp
namespace NGX.NET;

public struct NGXD3D12DLSSEvalParams
{
    public NGXD3D12FeatureEvalParams Feature;

    public nint Depth;

    public nint MotionVectors;

    public float JitterOffsetX;

    public float JitterOffsetY;
```

原生布局结构体：保留原生拼写（规范 §5.2），`[FieldOffset]` 与字段各占一行：

```csharp
[StructLayout(LayoutKind.Explicit, Size = 368)]
internal unsafe struct NGXD3D12DLSSEvalParamsNative
{
    [FieldOffset(0)]
    public NGXD3D12FeatureEvalParamsNative Feature;

    [FieldOffset(24)]
    public nint PInDepth;
```

转换构造函数：

- 局部模式变量命名为字段名的 camelCase（`depth`），不加 `item` 前缀（G8）。
- 逐字段赋值之间保持规范 §3.4 的分组：同类赋值紧凑，遇到需要 `if` 的分支前后空一行。
- 去掉不必要的 `this = default;`：结构体构造函数中，所有字段被赋值后不需要；若存在条件赋值的字段，保留该行。
- 原生结构体不再实现 `IDisposable`，构造函数不再包 `try`/`catch`：分配统一来自调用方传入的 `NativeScope`（§3.3）。只有转换时需要分配的结构体，构造函数才接收 `NativeScope` 参数。
- 只生成实际用到的转换方向。“托管 → 原生”只为作为输入出现的结构体生成；“原生 → 托管”只为作为输出出现的 6 个结构体生成（`NGXFeatureRequirement`、`NGXVkExtensionProperties`，以及创建 Vulkan 资源描述的辅助函数返回的 `NGXResourceVK`、`NGXImageViewInfoVK`、`NGXBufferInfoVK`、`NGXVkImageSubresourceRange`）。现状为每个结构体生成双向转换，其中 39 个“原生 → 托管”构造函数（807 行）与 2 个“托管 → 原生”构造函数（41 行）从未被调用。
- `NGXCoordinatesVK`、`NGXDLDenoiseCreateParams` 没有任何函数使用，只生成公共结构体，不生成原生类型与转换。

### 2.4 函数

#### 签名

- 公共方法参数名去掉 `p`/`pp`/`in`/`out` 前缀，缩写词整体小写：`pInParams` → `parameters`，`inUserSelectedWidth` → `userSelectedWidth`，`pOutRenderOptimalWidth` → `renderOptimalWidth`，`inSDKVersion` → `sdkVersion`（S2）。已用 `ast.json` 验证：1,084 个参数与字段名去前缀后没有任何重名；有 38 处会产生关键字 `params`，所以必须配合缩写展开（S6）。
- `[LibraryImport]` 的私有入口保留原生参数名（规范 §5.2）。
- 签名一律写在一行，不折行（S1）。

#### 输出参数

现状（节选自 `NGX.NET/API/DLSS.g.cs`，`GetStats`）：

```csharp
/// <summary>
/// NGX_DLSS_GET_STATS
/// </summary>
public static NGXResult GetStats(NGXParameter pInParams, out ulong pVRAMAllocatedBytes)
{
    pVRAMAllocatedBytes = default;
    ulong pVRAMAllocatedBytesNative = default;

    if (pInParams.IsNull)
    {
        throw new ArgumentException("A non-null NGX handle is required.", nameof(pInParams));
    }

    NGXResult result = GetStatsNative(pInParams.Value, &pVRAMAllocatedBytesNative);
    if (result is NGXResult.Success)
    {
        pVRAMAllocatedBytes = pVRAMAllocatedBytesNative;
    }

    return result;
}
```

目标：`[LibraryImport]` 入口对 blittable 输出直接声明 `out`，对句柄直接声明 `NGXParameter`，公共方法不再需要 `Native` 局部变量、`.Value` 与二次拷贝；失败时输出仍为 `default`（S7）：

```csharp
[LibraryImport(LibraryName, EntryPoint = "NGX_Bridge_NGX_DLSS_GET_STATS")]
[UnmanagedCallConv(CallConvs = [typeof(CallConvCdecl)])]
private static partial NGXResult GetStatsNative(NGXParameter pInParams, out ulong pVRAMAllocatedBytes);

public static NGXResult GetStats(NGXParameter parameters, out ulong vramAllocatedBytes)
{
    NGXResult result = GetStatsNative(parameters, out vramAllocatedBytes);

    if (result is not NGXResult.Success)
    {
        vramAllocatedBytes = default;
    }

    return result;
}
```

- 示例中省略了空句柄校验。按 D2，句柄保持值类型，公共方法保留该校验，生成为一行 `ArgumentNullException.ThrowIfNull((void*)parameters.Value, nameof(parameters));`：使用 BCL 为空指针提供的重载，不自写辅助方法，异常类型派生自现在抛出的 `ArgumentException`（D5）。
- 7 个输出的方法从约 21 行局部变量与拷贝降为 1 个调用加 1 个失败重置循环。多个输出的重置合并为一个 `if` 块。

#### 其他

- 内部指针局部变量使用规范 §15 允许的 `p`/`pp` 前缀（`pExtensions`），不再统一加 `Native` 后缀。
- 指针空比较使用 `is null` / `is not null`（V1 已验证可用）。
- 使用 `!`（null 宽恕）的位置仅限编译器无法推断的情形（规范 §10.2）；`storage!.` 的使用需要随第 6 节的结构调整一并消除。

### 2.5 回调与常量

- 删除 16 个 `NGXPfnParameterSet*`/`Get*` 委托（G12），它们对应的函数已绑定为 `Ngx.Parameter` 的方法；保留 3 个用户回调与 8 个参数表回调（§6.4）。删除属于公共 API 变化。
- 委托去掉文档注释；`[MarshalAs]` 属性按规范 §3.2 与参数写在同一行。
- `Constants.g.cs` 保持一个静态类的一组 `public const string`，常量之间不加文档；名称保持现有 SDK 派生名。

### 2.6 类型转换与返回值

### 3.3 互操作基础设施

#### 现状

| 类型 | 行数 | 职责 | 生成代码中的使用 | 问题 |
| --- | --- | --- | --- | --- |
| `NativeCall` | 59 | 一次调用的分配集合：字符串列表加 `NativeOwner` 链表；`HasFrameGenerationOptions` 标志 | `String` 17、`Take` 24 | 与下两个类型一起只实现了“一组分配一起释放”；DLSSG 的特例以标志位混入通用类型 |
| `NativeOwner` | 8 | 带 `Next` 字段的抽象基类 | 无（仅内部） | 只为把 `NativeValue<T>` 串成异构链表 |
| `NativeValue<T>` | 18 | 把一个原生结构体复制到堆上，释放时先 `Dispose` 再释放 | 经 `Take` | 只因为原生结构体各自负责释放内部分配才需要 |
| `NGXMarshal` | 180 | 公共的字符串转换，加内部的分配、释放、定长缓冲区读写 | `AllocNative` 73、`FreeNative` 73、`Free` 31、`StringToPtr` 16、`AllocValue` 11、`PtrToString` 7、`TextToPtr` 4、`WriteUtf8`/`ReadUtf8` 各 2 | 逐字段的分配与释放迫使原生结构体实现 `IDisposable`；内部工具暴露在公共表面；`WriteUtf8` 只被两个输出结构体的无用反向转换调用 |
| `NGXEncoding` | 17 | 公共枚举 `Utf8`/`NativeWide` | 44 处作为实参 | 编码在生成时已知，运行时又按枚举分支 |
| `NGXPointer<T>` | 35 | 让指针能作为 `[InlineArray]` 元素 | VK、CUDA 的 GBuffer | 只为释放时把元素转回类型化指针；D3D 的 GBuffer 直接用 `nint` |
| `NgxLifetime` | 248 | 全局注册表：5 个字典加 1 个集合 | 10 个方法、88 处调用 | 见 H3、H10；`PrepareParameters`/`RegisterParameters`（各 12 处）只为记录参数表属于哪个后端 |
| `NgxCallbacks` | 47 + 生成 | 委托根表加异常拦截 | `Acquire`/`Release` 各 9 | 根表与 `NativeCall` 的生命周期重复，委托可以直接由持有它的对象引用 |

它们在生成代码中带来的连带开销：47 个原生结构体全部实现 `IDisposable`，其中只有 13 个真正持有分配；`Dispose` 方法体约 504 行，另有 47 个构造函数级的 `try { } catch { Dispose(); throw; }`；API 方法中有 47 处 `xxxNative.Dispose()`、22 处带标志位的 `try`/`finally`、16 处为参数名写的 `try`/`finally`。

根本原因是每个原生结构体各自负责释放自己的嵌套分配。于是需要 `IDisposable`、构造失败回滚、堆上装箱（`NativeValue<T>`）、异构链表（`NativeOwner`）与逐字段释放（`FreeNative`）。规范 §15 给出的做法是“非托管内存由负责统一释放的作用域对象分配”：改为一次调用的全部分配来自同一个作用域对象，上述机制都不再需要。保留内存也不再是“保留若干个结构体”，而是“保留一个作用域对象”。

#### 目标类型

| 类型 | 职责 | 取代 |
| --- | --- | --- |
| `DisposableObject` | 规范 §13 的统一释放基类，代码与 Zenith.NET 相同 | `NativeOwner` |
| `NativeScope` | 一次调用或一次保留所需的全部原生分配与回调委托，`Destroy()` 一次性释放 | `NativeCall`、`NativeOwner`、`NativeValue<T>`、`NGXMarshal` 的分配部分、`NgxCallbacks` 的根表 |
| `NativeLifetime` | SDK 在调用后仍会引用的 `NativeScope` 与 CUDA 设备地址（§6.1） | `NgxLifetime` |
| `NativeTextHelper` | `ReadUtf8(ReadOnlySpan<byte>)` 读取定长缓冲区（到第一个 NUL 或缓冲区末尾）；`ReadWide(void*)` 读取 `wchar_t*` | `NGXMarshal` 的读取部分 |
| `CallbackGuard` | 3 个用户回调的异常拦截包装：`Wrap(NGXAppLogCallback)`、`Wrap(NGXPfnProgressCallback)`、`Wrap(NGXPfnProgressCallbackC)`，以及通过 `Trace` 报告的 `Report` | `NgxCallbacks`、`NgxCallbacks.g.cs` |
| `NativeLoader` | 见 H7、H8 | `Ngx` 的静态构造函数 |

以上类型均为 `internal`。删除 `NGXEncoding`：生成器按 `char`/`wchar_t` 直接调用 `AllocUtf8`/`AllocWide`。删除 `NGXPointer<T>`：VK、CUDA 的 GBuffer 元素改为 `nint`，与 D3D 相同，释放由 `NativeScope` 负责，不再需要转回类型化指针。

`NativeScope` 的成员：

| 成员 | 说明 |
| --- | --- |
| `T* Alloc<T>(in T value)` | 把一个值复制到原生内存 |
| `T* Alloc<T>(int count)` | 清零的数组（路径列表、GBuffer 元素） |
| `byte* AllocUtf8(string? value)` | `char*`；`null` 返回 `null` |
| `void* AllocWide(string? value)` | `wchar_t*`：Windows 上为 UTF-16，其他平台为 UTF-32 |
| `nint Keep(Delegate callback)` | 返回函数指针，委托由 scope 的字段持有，与 scope 同生命周期（规范 §15） |
| `Destroy()` | 释放全部分配，清空委托引用 |

其余由 .NET 自带机制承担：

- 调用期内的 UTF-8 字符串（`Ngx.Parameter` 16 个 `Get*`/`Set*` 的参数名）由 `[LibraryImport(..., StringMarshalling = StringMarshalling.Utf8)]` 直接接收 `string`，短字符串在栈上转换。511 个参数键常量均为 ASCII（74 个含 `\x00`–`\x49` 转义），编码结果与现在逐字节相同。
- 读取 UTF-8 指针（Vulkan 扩展名数组）用 `Marshal.PtrToStringUTF8`。
- 4 个后端的 `EvaluateFeature`/`EvaluateFeatureC` 的进度回调只在调用期间使用：局部变量持有包装后的委托，调用后 `GC.KeepAlive`，不为此分配 scope。
- 没有采用 `[NativeMarshalling]` 自定义封送器：它在调用结束时释放内存，无法表达跨调用保留，而与作用域对象并存会形成两套机制。

## 6. 结构调整

以下内容不是风格问题，但决定第 2、3 节中部分输出的形态。决定与依据见 §8.2、§8.4。

### 6.1 句柄与保留内存（D2）

- `NGXParameter`、`NGXHandle` 保持只读结构体，保留 `Value`、`IsNull` 与相等比较，删除 `Deconstruct`。释放仍由显式调用完成（`DestroyParameters`、`ReleaseFeature`、`Shutdown`）。
- 库继续代为保留 SDK 在调用返回后仍会引用的内存，README 中的契约不变：成功的调用替换旧内容，失败的调用保留已写入的内容，DLSSG 省略可选参数时保留上一次的矩阵，`Reset`、`DestroyParameters` 或关闭后端时释放；初始化的字符串、路径与日志回调保留到成功关闭。
- 只保留 SDK 确实会继续引用的内存。依据 SDK 头文件：
  - 需要保留：Vulkan 辅助函数用 `SetVoidPointer` 写入 `NVSDK_NGX_Resource_VK*`（`nvsdk_ngx_helpers_vk.h`、`nvsdk_ngx_helpers_dlssd_vk.h`）；DLSSD 写入两个矩阵指针（`nvsdk_ngx_helpers_dlssd_vk.h`；D3D 版本的头文件不在本地副本中，按下文的类型规则同样保留）；DLSSG 只在提供可选参数时写入指向该结构体内部数组的指针（`nvsdk_ngx_helpers_dlssg_d3d.h`、`nvsdk_ngx_helpers_dlssg_vk.h`）。
  - 不需要保留：`nvsdk_ngx_helpers_d3d.h` 中没有任何 `SetVoidPointer`，D3D11/D3D12 的 DLSS 与 DLISP 辅助函数只写入用户持有的资源指针与标量（例如 `NGX_D3D12_EVALUATE_DLSS_EXT` 中 `SetD3d12Resource` 30 次、`SetUI` 15 次、`SetF` 8 次、`SetI` 3 次）。这类评估参数改为在栈上转换后直接传入，逐帧调用不再分配。
  - 生成器的判断只有一条：转换需要 `NativeScope`（有分配，或结构体含会被 SDK 取址的内联数组、需要整体放进 scope）即保留，不按函数名列举。
- `NgxLifetime` 改写为 `NativeLifetime`（§3.3），只保存 `NativeScope`，以 `NGXGraphicsAPI`（`Cuda`、`D3D11`、`D3D12`、`Vulkan`）代替 `"D3D12"`、`"CUDA"` 等字符串键，用 `Lock` 作用域保护：

| 成员 | 调用时机 | 行为 |
| --- | --- | --- |
| `Retain(NGXGraphicsAPI api, nint device, NativeScope scope, NGXResult result)` | 初始化返回后 | 成功则保留到关闭，失败则立即释放 |
| `Release(NGXGraphicsAPI api, nint device)` | `Shutdown`/`Shutdown1` 成功后 | 释放该设备（`device` 为 0 时为整个后端）的初始化 scope；后端没有剩余设备时，一并释放该后端的参数表 scope 与 CUDA 设备 |
| `Retain(NGXGraphicsAPI api, NGXParameter parameters, string slot, NativeScope scope, NGXResult result)` | 辅助函数返回后 | 成功则先释放同一槽位的旧 scope，失败则与旧 scope 并存 |
| `Release(NGXParameter parameters)` | `Reset`、`DestroyParameters` 成功后 | 释放该参数表的全部 scope |
| `GetCudaDevice(in NGXCUDADevice device)` | `Init1`、`CreateFeature1`、`Shutdown1` 等 | 按 `(context, stream)` 返回稳定地址 |

- 槽位按“函数 + 参数”划分。DLSSG 的可选参数单独一个槽位，省略时不触碰该槽位，“保留上一次矩阵”由通用规则得到，不再需要 `HasFrameGenerationOptions`。
- 每个保留项记录自己的后端，不再需要 `PrepareParameters`/`RegisterParameters` 维护“参数表 → 后端”的映射。
- CUDA 设备副本只在关闭时释放，去掉 `activeCudaDevices` 与 `FinishCudaDevice`。
- 在原生调用返回后登记，删除为内存不足准备的回滚与预分配（H3、H10）。生成的方法体随之去掉 `attached`/`returned` 标志与 `storage!.`（G7）。

### 6.2 结构体对

47 个 `Native` 类型中：13 个持有分配，12 个包含必须转换的字段（`bool`↔`NGXBool8`、`nint`↔`void*`、回调、可选成员、数组），这 25 个保留双层；20 个无嵌套分配且托管与原生字段列表完全一致（共 2,875 行），可合并为一个带 `[StructLayout]` 的公共类型。合并后须通过现有布局与偏移检查。Vortice 对含数组、字符串的结构同样采用“托管类型 + 原生布局”两层，并在调用前后转换与释放（`__Native` 与 `__MarshalTo`/`__MarshalFree`），保留这 25 对与参考库一致。

### 6.3 错误处理（D1）

- 每个函数返回 `NGXResult`，输出用 `out`，这是完整的 API。
- 只有一个输出的函数，另生成一个返回该值、失败时抛 `NGXException` 的重载；没有输出或有多个输出的函数不生成。删除结果结构体、`Emitter.Results.cs` 及 README 中的类型名推导规则，也不改用元组。
- `NGXResult` 增加公共扩展成员 `IsSuccess`、`IsFailure` 与 `CheckError(string? operation = null)`，判断规则与 SDK 宏 `NVSDK_NGX_SUCCEED`/`NVSDK_NGX_FAILED` 相同：`(value & 0xFFF00000)` 是否等于 `NVSDK_NGX_Result_Fail`。现有 19 个失败值都在该掩码内，对现有值的判断与 `== NGXResult.Success` 一致。生成代码、抛异常的重载与 README 统一使用这组成员。
- 失败时 `out` 输出重置为 `default`（S7）。

### 6.4 回调（D3）

- 3 个用户回调（`NGXAppLogCallback`、`NGXPfnProgressCallback`、`NGXPfnProgressCallbackC`）保持委托类型，由 `CallbackGuard.Wrap` 包装：异常通过 `Trace` 报告，进度回调出错时请求取消。
- 日志回调在转换 `NGXLoggingInfo` 时由初始化的 `NativeScope` 持有（`Keep`），与初始化字符串一起保留到后端关闭；进度回调只在 `EvaluateFeature`/`EvaluateFeatureC` 调用期间使用，由局部变量持有并在调用后 `GC.KeepAlive`。不再维护以函数指针为键的根表，生命周期与现状相同。
- 8 个参数表回调保留委托类型。它们经 `Ngx.Parameter.SetVoidPointer` 以地址传入，由调用方保持委托存活，与 README 中“以原始地址手动注册的回调”的约定一致。
- 删除 16 个 `NGXPfnParameterSet*`/`Get*` 委托（G12）。

### 6.5 验证范围

- 保留：布局/偏移/枚举值/入口名与 AST 一致；公共表面无指针；生成器输出确定；转换层的边界行为。
- 改写：保留语义（替换、失败保留、DLSSG 省略选项、`Reset`/销毁/关闭时释放）改为针对 `NativeLifetime` 的接口编写，不再反射读取私有字段。
- 删除：结果结构体相关检查。
- 新增：D3D11/D3D12 DLSS 评估路径不产生托管与非托管分配。

### 6.6 二进制（D4）

现状：`build_ngx.py` 为每个头文件生成一个翻译单元，内容只有 `#include` 行（`parse_ngx_ast.py` 中的 `prologue`）和为每个 `inline` SDK 函数生成的一行 `extern "C"` 转发，不含 NVIDIA 头文件的内容（上一版说它包含头文件的完整拷贝，有误）。这些源码在 CI 中编译后即丢弃，仓库里只有二进制；LLVM、`libclang`、Python、`actions/*@main` 与 ARM 运行器标签都取“最新”；更新结果直接推送到触发分支。

决定：

- 生成的 bridge 源码随二进制一起提交，放在 Git LFS 之外的 `bridge/<rid>/`（`native/**` 走 LFS，放在其下无法直接查看差异），每次二进制变化都有对应的源码差异。
- 运行器镜像、LLVM、`libclang`、Python 与各 Action 写明版本。SDK 仍取 NVIDIA 最新 release，这是更新流程的目的，其 release 与 commit 已记录在 `ast.json` 的 `source` 中。
- 更新流程把结果提交到独立分支并创建 PR。
- 不另加二进制清单：源码入库、工具链固定、经 PR 合入之后，清单中的信息都能从仓库得到。

### 8.2 结构决策

**D1 错误处理**（§6.3）

- 决定：`NGXResult` + `out` 为完整 API；单输出函数另有返回值、失败抛 `NGXException` 的重载；多输出不生成抛异常重载，删除结果结构体，不用元组；`NGXResult` 增加 `IsSuccess`、`IsFailure`、`CheckError`，规则同 `NVSDK_NGX_SUCCEED`/`NVSDK_NGX_FAILED`。
- 依据：Vortice 为创建类 API 成对提供 `T CreateX(...)`（内部调用 `.CheckError()`）与 `Result CreateX(..., out T?)`；多输出的 `CheckFormatSupport(format, out ..., out ...)` 只用 `out`；两个参考库都没有聚合结果类型或元组。SharpGen 的 `Result.Success`/`Failure` 对应 Win32 的 `SUCCEEDED`/`FAILED` 宏，NGX 的对应物是上述两个 SDK 宏。

**D2 句柄与保留内存**（§6.1）

- 决定：句柄保持只读结构体，删除 `Deconstruct`；库继续代为保留 SDK 会继续引用的内存，但只保留确实被引用的部分，并改写为 `NativeLifetime` 的成对接口；公共方法保留空句柄校验。上一版建议把句柄改为对象，不采纳。
- 依据：Silk.NET 的 `Instance` 是只含 `nint Handle` 的结构体，由显式的销毁调用释放；Vortice 的 `CpuDescriptorHandle` 是带相等比较的结构体，只有引用计数的 COM 对象才做成类。NGX 的句柄没有引用计数，释放函数取决于后端，旧式 `GetParameters` 的结果还不能销毁，属于前一类；参考库的句柄结构体都没有 `Deconstruct`。跨调用保留内存对应 Silk.NET `SilkMarshal` 以指针为键的全局表（`_marshalledMemory`、`_otherGCHandles`），区别只在释放时机由 SDK 的生命周期决定；不被 SDK 引用的内存在调用后立即释放，与 Vortice 的 `__MarshalTo`/`__MarshalFree` 相同。参考库不做空句柄校验；这里保留，是因为头文件中的辅助函数把参数表指针直接交给 `NVSDK_NGX_Parameter_*`，没有空检查，`default` 句柄会让进程在原生代码中崩溃，与“安全方法”的职责冲突。

**D3 回调**（§6.4）

- 决定：用户回调保持委托并拦截异常；日志回调由初始化的 `NativeScope` 持有到后端关闭，进度回调在调用期间保活（§3.3）；不改用 `[UnmanagedCallersOnly]` 静态入口；删除 16 个已绑定函数的指针委托。上一版建议改为静态入口，不采纳。
- 依据：Silk.NET 同样把托管委托转为函数指针交给原生代码，并由库保持其存活直到显式释放（`SilkMarshal.DelegateToPtr(pinned: true)` 与 `Free`）；这里改由持有它的 `NativeScope` 的字段保活（规范 §15），生命周期与现状相同。静态入口会把每种回调限制为一个注册者，参考库中没有这样处理用户回调的先例。

**D4 二进制**（§6.6）

- 决定：生成的 bridge 源码与二进制一起提交；固定运行器与工具链版本；更新经 PR 合入；不另加清单。上一版建议“源码只作为 CI 构件、另加清单”，不采纳。
- 依据：Silk.NET 把所有原生依赖的源码以子模块固定在仓库中（如 `build/submodules/GLFW`），工作流使用固定版本的运行器（`ubuntu-22.04`、`windows-2022`、`macos-14`），新二进制由 `PrUpdatedNativeBinary` 提交到 `ci/<branch>/<name>_bins` 分支并创建 “Update {name} binaries” PR。参考库没有单独的二进制清单。

**D5 互操作基础设施**（§3.3）

- 决定：以 `NativeScope`、`NativeLifetime`、`NativeTextHelper`、`CallbackGuard`、`DisposableObject` 取代 8 个手写类型；§3.3 的 5 项行为变化已确认。空句柄校验写作 `ArgumentNullException.ThrowIfNull((void*)handle.Value, nameof(handle))`。
- 依据：规范 §15（非托管内存由负责统一释放的作用域对象分配；委托由字段持有）与 §13（`DisposableObject`）；调用期内的字符串使用 .NET 自带的 `StringMarshalling.Utf8`。空句柄就是空的 `NVSDK_NGX_Parameter*` 或 `NVSDK_NGX_Handle*`，BCL 为空指针专门提供了 `ArgumentNullException.ThrowIfNull(void*, string)`。`ArgumentOutOfRangeException.ThrowIfZero` 会把句柄描述为数值范围错误（“handle ('0') must be a non-zero value.”），不采用。两者的消息已在 .NET 10 上实测。
